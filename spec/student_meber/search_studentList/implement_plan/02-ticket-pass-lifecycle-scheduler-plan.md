## 1. 已確認的邊界

- 使用者要求將生命週期排程放到最後階段處理，目前尚未實作。
- 學員列表查詢維持唯讀，不藉進入列表頁觸發結束或啟用票券。
- 排程未完成前，列表可修正已過期 Active 的顯示，接受下一張票尚未立即啟用的過渡行為。
- 排程不應改變已確認的購票、續約、取消或單堂票啟用規則；實作前需讀取並核對其現行規格與程式。

## 2. 待討論的設計建議

下列是前次討論提出的建議，不代表排程參數已定案。

| 項目 | 建議方向 | 仍需確認 |
| --- | --- | --- |
| 主要更新 | 台灣跨日後執行一次 | 執行時間與可接受延遲 |
| 補查 | 每 30 分鐘補查 | 頻率、負載與批次大小 |
| 停機恢復 | 服務啟動時補查 | 部署方式、啟動期間是否阻塞 |
| 補查範圍 | 找所有目前已需處理的票，而非只查昨天 | 候選學員 SQL、歷史異常資料處理 |
| 共用流程 | 沿用生命週期協調流程，處理結束、下一張啟用、單堂票讓位、profile 快照 | 既有流程是否可安全供批次調用 |
| 交易 | 以學員為單位，沿用既有鎖定，重複执行結果一致 | 與付款、取消、扣堂併發時的行為 |
| 即時處理 | 保留購買、付款、取消的即時更新 | 扣堂／核銷目前是否完整串接，需查程式 |
| 執行方式 | 待選擇後端 background service 或其他排程機制 | 多實例重複執行、服務停機時的運作 |

既有其他查詢是否應移除生命週期副作用需另確認，本計畫不自動擴大到所有查詢。

## 3. 定案後的實作順序

1. 核對現行票券／續約規格、ReconcileCurrentAsync 呼叫點、時鐘與交易／鎖定。
2. 與使用者確認執行機制、頻率、候選範圍、併發及失敗處理，將上表改成已定案規格。
3. 實作共用批次入口與候選查詢，不複製另一套票券狀態機。
4. 串接排程、啟動补查、必要的重試與執行紀錄。
5. 驗證日期邊界、停機補查與併發，更新狀態文件。

## 4. 建議驗收案例（尚待定案）

- 台灣到期日當天不提早結束，隔天能處理過期與後續票。
- 停機跨日或停機數天後，補查不遺漏較早過期的票。
- 同一批重複執行不重複啟用、不產生多張 Active、不遺失剩餘堂數。
- 有可啟用的非單堂票時，單堂票回到 UnActive 並保留堂數；非單堂票結束後依規則再使用單堂票。
- 付款／取消／核銷與排程同時執行時，票券與 profile 一致，續約來源不被重複占用。
- 單一學員處理失敗不造成整批永久停滯，後續可重試並查到失敗原因。
- 在無人開啟列表時仍能更新；列表查詢持續唯讀。
