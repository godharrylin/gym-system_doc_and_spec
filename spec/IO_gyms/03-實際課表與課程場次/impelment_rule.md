# 階段 03：實際課表與課程場次

建立日期：2026-10-04。確認／更新日期：2026-10-10。

引用同步日期：2026-10-15。僅對齊第四階段 IO-02 已確認的時段規則，未變更本階段核心決策或實作功能。

狀態：第三階段主要程式核心已實作並通過自動驗證；瀏覽器人工驗收待執行。未新增資料表或修改 GymDB schema。

依據：[規格](../gym-io-behavior-spec.md)、[issue](../issue/gym-io-issues.md)。

## 目標與範圍

讓課表頁面、進場判斷與背景工作使用同一份實際場次，避免以週模板或前端 mock 直接計算出席。

## 已確認的第一版規則

- 一間教室、同一時間一堂課；票券不綁課程。
- 課程需穩定場次 ID、開始／結束時間及老師，作為出席與結算的關聯。
- 前端頁面、進場判斷與背景流程共用同一份實際場次，不以 mock、課名或前端自行拼出的 ID 結算。

### 1. 場次即時生成，固定排程延後

- 趕上線的第一版保留原行為：載入／查詢未生成的週時，即時由啟用模板產生實際場次，不先實作固定每週生成排程。
- 維持既有星期一至星期日的週範圍及 weekStart 正規化方式；不能把先前星期日排程提案當作已實作功能。
- 只有整週完全沒有任何場次時才生成。有任一場次就直接回傳，不逐堂补齊其他模板，不覆寫既有人工修改。
- 已取消場次也是既有資料；即使該週全部取消，也不因再次查詢從模板復活。
- 模板異動不回寫已存在的實際場次；只在後續尚未生成的週使用當時模板。
- 背景流程可共用相同應用服務／repository 取得或確保場次，不依賴有人打開瀏覽器頁面，也不繞 HTTP 呼叫自己的 API。
- 先前「星期日 00:00 固定生成」改列後續擴充，未定義目標週、補跑等參數前不自行加入。
- 延後的是課表生成排程，不是出席 A／扣堂 B；A／B 仍由階段 04／05 規劃。

### 2. 課程開始後禁止所有編輯及取消

- 開始前允許修改、取消、更換老師，仍需符合既有課程／老師有效性、衝堂及操作者權限。
- 到達原場次開始時間後，禁止所有課程編輯及取消，包含老師、課程種類、名稱、時間／長度、免費標記與狀態變更。
- 以後端 IClock 的台灣時間與原始 StartAt 判斷，不信任前端時間、不只停用按鈕、不先把課改成未來再逃過限制。
- 使用 `now >= originalStartAt` 作已開始的判斷；不能只靠 DB 是否已被排程改成 Ongoing／Finished。
- 編輯應保留實際場次 ID 與既有異動紀錄，不能刪掉重建來規避已開始限制。
- 日後開始後代課／特殊修正需獨立規則，不在第一版自行開例外。

### 3. 至少十分鐘的課程間隔

- 保持既有至少十分鐘間隔，不改成只有時間區間重疊才拒絕。
- 例如上一堂 20:00 結束：20:00 或 20:05 開始的下一堂拒絕；20:10 開始允許。
- 新增／修改都由後端作最終檢查，前端將衝堂原因顯示成使用者可理解的警告。
- 間隔是排課規則，與開課／下課十分鐘後的 A／B 是不同用途。

### 4. 免費標記不免除票券資格及扣堂

- 免費課程仍驗證票券，堂票仍需占用並由 B 扣堂；月票沿用出席不扣堂數的既有規則。
- `isFree` 不作為繞過學生票券資格、遲到限制或扣堂的理由。
- 本階段提供正確場次與免費標記，不直接實作 A／B 或扣堂。

## 已核對的程式現況（不等於本輪已實作）

- 後端已有 `GET /api/v1/admin/schedule-session/week?weekStart=yyyy-MM-dd`，空週時會建立場次，不是純讀取。
- `GetOrEnsureScheduleWeekHandler` 在 existingSessions.Count > 0 時不生成，已取消場次不由查詢重建。
- 前端原先使用 `MockClassRepository`；本次已改接 API repository，使用資料庫真實課程 ID、老師 ID 與實際場次 ID。
- 前端原先沒有後端衝堂警告；本次已顯示 API 錯誤並保留編輯內容。新增／修改沿用後端十分鐘間隔檢查。
- 課程、老師、模板及場次管理 API 明確要求 Admin role；既有場次修改 handler 另保留 Admin／Staff 檢查，兩層條件同時生效時仍只有 Admin 可操作。
- 台灣日期字串使用本地日期 helper；場次詳情不再以 mock 產生虛構出席名單。
- 開始時及之後的場次編輯／取消由後端依 `IClock.Now() >= 原始 StartAt` 拒絕，前端保留表單並顯示拒絕原因。

## 前置依賴與預計項目

1. 核對實際場次 model、資料表、查詢及週起日／台灣日期轉換。
2. 保留查詢空週即時生成，以 transaction-owned SQL application lock 串行同週查詢／生成與手動新增／異動；不新增每週排程或資料表。
3. 課表頁改接 API，保留實際場次 ID，不自行用日期與課名合成結算識別。
4. 背景工作共用後端服務／repository，不透過前端頁面執行才取得課表。
5. 落實至少十分鐘衝堂檢查、開始後全編輯／取消拒絕與場次 ID 穩定性，更新前後端錯誤呈現。
6. 核對 API 權限，避免只以路徑 `admin` 推定已限制 Admin。

## 驗收案例

- 頁面與背景用例讀到同一場次 ID、時間及老師。
- 跨週、月、年及台灣午夜附近日期正確。
- 空週生成，重查不重複；已有一堂手動場次不補其他模板；全取消不再生成，查詢結果仍依既有規則排除 Cancel。
- 模板沒有啟用資料時回傳空結果，不假造課程；有模板時頁面與背景得到同一份場次。
- 上一堂 20:00 結束，下一堂 20:00／20:05 拒絕，20:10 允許；修改既有場次不把自身判為衝堂。
- 開始前可修改／取消／換老師，開始時及開始後所有編輯／取消拒絕；用原始時間及後端時鐘，不能改時間逃過限制。
- 免費課程不繞過資格／堂票扣堂：此階段核對標記及契約，實際扣堂在階段 04／05 驗收。
- 前端顯示後端拒絕原因且保留輸入；API 直接呼叫也不能繞過開始時間／權限／衝堂限制。
- 模板修改不意外改寫已存在的出席或歷史结算。

## 本階段不包含

固定每週課表生成排程、出席名單、堂數扣除、館內狀態更正及完整課程管理功能重寫。原每週星期日排程提案列後續擴充，需另定目標週、重啟補跑與已存在資料的處理；不因此延後 A／B。
