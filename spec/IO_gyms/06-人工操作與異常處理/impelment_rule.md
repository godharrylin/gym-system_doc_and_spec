# 階段 06：人工操作與異常處理

建立日期：2026-10-04。狀態：第一版主要商業規則已確認，待技術設計、實作及驗收；不代表所有例外案件均能一鍵處理。

同步日期：2026-10-16。彙整人工放行、當下生效的館內狀態更正、獨立出席／扣堂更正、台灣午夜換日、人工確認後恢復及學生詳細頁入口的決策。本輪只更新文件，未修改程式或 DB，未執行功能驗收。

依據：[規格](../gym-io-behavior-spec.md)、[issue](../issue/gym-io-issues.md)。

## 目標與範圍

提供後台操作者人工進／出、館內狀態更正與異常處理，保留完整理由及追溯性。

## 已確認規則

- 人工放行與館內狀態更正分開；更正不需要轉動三叉機。
- 操作選進／出，理由必填，保存操作者與結果。
- 保留異常，包括過期、負堂數與不一致狀態。
- 留館缺票記 Ineligible 與原因，不欠堂、不扣負數、不補結算，不授予回場資格；保存已存在的負數異常不代表允許新的負數扣堂。
- 跨日殘留館內狀態不應自動算進新課程。
- 忘記出場議題保留；沒有實際通行回饋不能推定真實離場時間。
- 階段 05 已確認逐學生結算與失敗隔離；上一堂未完成者暫停其下一堂資格確認，不阻擋其他人，不把處理失敗直接當作無票或 Ineligible。
- 固定占用後票券／堂數變更造成衝突：停止該筆自動結算、記錄原因並轉人工，不換票、不扣負數、不標完成。
- A 歷史不足以可靠還原：保存待人工確認與缺漏原因，不用現在名單推定出席或扣堂。
- 原本 Ineligible 不補結算；原本 Eligible 的結算故障不能直接套用此規則結案，依本文件已確認的人工重新驗證與恢復流程處理。
- 階段 05 保存工作狀態、原因、預定／實際時間及重試紀錄；暫時性錯誤可恢復重試，資料衝突不以按重試強制扣堂，已完成項目不得重扣。

## 第 1 項已確認：人工放行的權限與繞過範圍

確認日期：2026-10-15。本節為目標規則，不代表兩個入口已完成所有實作。

### 1. 操作權限與紀錄

- 第一版人工放行只允許登入後台的 Admin；iPad 裝置授權不能取代 Admin 權限，Staff／Instructor 不因其工作人員進場資格而取得人工放行權限。
- 後端必須驗證操作權限及操作者身分；IP／內網限制是額外防線，不取代 API 授權。本輪未核實實際部署的 IP 隔離。
- 操作選進／出，理由必填，保存實際操作者、方向、時間及結果；操作者是 Admin 不代表被代操作的學生改以 Admin 身分入場。

### 2. Students & Members：正常人工進／出

- 沿用各學生 Actions 中目前停用的 Manual Check-in 入口，後續規劃為 Manual Check-I/O，供 Admin 代該學生操作。
- 人工進場共用正常進場資格驗證：票券、課程時間、額度、回場資格及相關限制都不能繞過；學生遲到不透過此入口通融上課。
- 對已識別使用者的人工出場，維持不因帳號／角色停用、profile 缺漏、票券過期、額度不足或課程時間而阻擋的既有規則。
- 正常人工進／出只有廠商成功回應才記錄成功進出並更新會員館內狀態；事件時間沿用後端收到成功回應時間，不回填較早時間。
- 出席、暫占及扣堂仍依 A／B 和正常生命週期規則，不因人工開門而直接補認出席或立即扣堂。
- 原本正常進場的學生要由後台協助離場，使用此正常人工出場，不使用 Device Test 代替。

### 3. System Settings > Device Test：只開門的取物放行

- 原本在館外、只是臨時進來拿東西者，進／出都使用 Device Test 的對應方向；不另建一個例外放行頁面。
- 這是設備控制／取物用途，不是學生上課授權入口；不建立會員正常進出紀錄、不改會員館內狀態、不建立或補認出席、不占用或扣堂，也不授予同堂回場資格。
- 不把遲到、無有效票券等學生透過取物放行改成可上課；背景工作不得把這類設備操作當作出席證據。
- 原本已有正常館內狀態者不得以取物放行代替正常出場，避免系統仍誤認在館內。
- 取物放行仍須保存操作理由與操作者／結果，並可辨識與純設備測試的不同用途；具體 UI、契約與稽核儲存設計待實作前核對，不將現有設備測試日誌視為業務稽核已完成。

### 4. 操作錯誤與狀態更正的分界

- 已經操作錯誤造成館內狀態不一致，交由獨立的「館內狀態更正」流程處理，不改寫原始進出或設備操作紀錄。
- 更正不發送開門指令，只從後端操作當下生效，不回填過去的實際進出時間，也不自動修改歷史出席／占用／扣堂。
- 回溯出席與扣堂由獨立更正案件處理，不能以館內狀態更正繞過資格、截止及稽核要求；詳見下節。

### 5. 已查閱的入口現況與待對齊差異

- 前端 StudentListPage 目前按鈕為停用的 Manual Check-in，尚未完成正常人工進／出的操作流程。
- Device Test 已有 Admin API 授權及操作者檢查；目前請求只有方向，handler 依 DeviceTestEnabled 設定發送命令，沒有會員出席／進出寫入。
- Device Test 目前已有操作者、方向、結果與追蹤編號的應用程式日誌，但未提供取物理由及用途欄位，不代表已完成上述取物業務稽核。
- 現況依本輪討論期間的唯讀原始碼核對，不代表已完成設備測試、部署限制或人工場地驗收。

## 已確認：館內狀態與歷史出席分開更正

以下彙整至 2026-10-16 的決策，不表示已實作。

### 1. 館內狀態更正只當下生效

- Admin 現場確認後，更正目前在館內／館外狀態；理由必填，保存前後狀態、操作者及後端台灣時間，不呼叫三叉機、不覆寫原始事件。
- 不自動改變過去截止名單、釋放過去固定占用或退回已扣堂數；如涉及歷史錯誤，另外建立出席／扣堂更正案件。
- 更正後的狀態可供後續正常截止判斷使用，但仍須通過票券、額度等資格驗證，不能把更正為在館內當成直接授予 Eligible。
- 已確認出席者中途離場，即使未回仍照原規則結算；不能只因目前更正為館外就撤銷該堂出席。

### 2. 獨立出席／扣堂更正

- 第一版允許撤銷誤判出席，以及補認原本符合原截止時刻條件、但被漏記的出席。
- 每次以學生＋實際場次為對象，檢查原票券、占用、扣堂及歷史依據；不依現在 Current Plan 重選票，不拿事後付款補原本沒有的資格，不作遲到通融。
- 原本正確的 Ineligible 仍不補結算；歷史不足先待確認，不以現在在館內推定過去出席。
- 撤銷尚未扣堂的誤判出席：保存更正歷史，撤銷有效出席並釋放原占用。若已正式扣堂，須新增對應原 Consume 的 Reverse，不刪原核銷紀錄。
- 沖銷限整筆退回原扣堂，不允許任意輸入加減堂數；月票只更正出席，沒有堂數增減。
- 補認漏記出席需核對歷史資格及額度，經共用占用／結算服務處理，不另寫一套直接扣額度流程；歷史更正不改學生現在的館內狀態。
- 2026-10-25 防重決策：人工 Consume 記 usage_type = Manual，並在同一交易扣堂、寫核銷、連結占用 usage_sn／Consumed 及結算進度；B 取得鎖後查同一 attendance_sn 的 Consume，核對一致則不再扣。usage_type 不代替出席關聯，不新增 ManualDeducted 出席狀態，也不新增核銷 idempotency_key 或扣堂唯一約束。直接 SQL 改餘額不會自動成為已完成本堂核銷；新人工入口須使用共用服務。
- 第一版由 Admin 自己確認並執行，不另設第二位人員審核；後端仍重驗權限、原因與最新資料，不提供略過驗證的強制成功按鈕。

### 3. 第一版不提供一鍵處理的案件

- 已影響後續票券啟用：保存 NeedsReview 原因，先不退堂、不把舊票直接恢復 Active，不自動回滾接續票券或重算其效期。
- 同堂已撤銷／沖銷後又要求再次補認，屬反覆更正：轉待人工確認，不提供一鍵再次扣退；不能藉新 request_id、重建出席或背景重跑繞過。
- 上述案件可以保存及查閱，但更進一步的專案例外解決方式留後續設計；第一版不以直接修改 DB 作為已完成的解法。

### 4. 更正案件、稽核與交易

- 沿用 sdt_att_record 與 sdt_ticket_usage_log，新增 sdt_att_correction 保存申請／進度，及 sdt_att_record_audit_log 保存出席變動前後快照；欄位、CREATE 與實作限制見 [Database.md](../../../Database.md)。只有文件設計，不代表 GymDB 已建表。
- 申請進度可更新，實際出席變動另新增不可覆寫的稽核；保存原因、依據、真實操作者、業務時點與實際處理時間，原 Consume／成功進出紀錄不刪除。
- 出席、占用／額度、Consume／Reverse、出席稽核及案件完成標記須一致提交；同一次請求不得重複執行，同一原 Consume 不得重複沖銷。
- 既有表的結算狀態、撤銷表示法、唯一性與並行控制仍待技術設計；不把兩張新表的 CREATE 當作更正功能已完成。

## 已確認：忘記出場與跨日殘留

- 第一版以台灣日曆日午夜 00:00 換日，適用目前沒有跨夜課程的前提；不是跨午夜自動扣一堂，也不是午夜強制建立出場。
- 昨日未結束的館內狀態保留為跨日待確認，不刪歷史、不生成假的午夜出場，不直接當成今日仍在館內或建立今日出席。
- 跨日待確認屬館內狀態異常，不等於票券 Ineligible；實際欄位及狀態代碼待技術設計，不直接擴充票券資格 enum。
- 今日正常進場須重新驗票、課程時間及額度，廠商成功回應後建立今日狀態；不得僅因昨日殘留在館內而拒絕本次正常進場。
- 人確實仍在館內時，Admin 可現場確認並由館內狀態更正從操作當下建立今日有效狀態；不回填成今日較早時間。
- 若到今日該堂截止仍未重新確認，不憑昨日殘留自動認出席；需要補認時改走有歷史依據的出席更正流程。
- 已識別使用者出場仍可放行，不因跨日待確認阻擋；取物 Device Test 不建立今日出席依據。
- 進出 API、出席確認及狀態查詢共用日期檢查，不完全依賴午夜排程；即使午夜服務未啟動，隔日也不能沿用昨日狀態。主動整理清單的背景工作可後續擴充。
- 昨日已固定的出席／占用不因換日清除。2026-10-23 最新確認：跨日仍未完成的 A／B 一律 NeedsReview，包含 A 已固定而 B 未完成的情況；不自動補扣、啟用接續票或重算歷史效期。人工仍依原固定資料及證據重驗，不能重新選今天的票倒補昨天，已完成項目不得重扣。

## 已確認：第一版入口與人工確認後恢復

確認日期：2026-10-16。

### 1. 入口與顯示資料

- 第一版正式處理入口放在學生詳細頁；Schedule 保持排課用途，不新增結算操作。獨立 Classes 課程營運總覽頁列後續擴充，不是新增資料表或另一套結算服務。
- 2026-10-23 已接受第一版不建立完整歷史重播架構的代價：跨日未完成 A／B 均由此入口查閱原因、確認及恢復，即使已固定的 B 原本可能安全自動結算也轉人工。入口仍為第一版必要待實作項目；只有 NeedsReview 儲存而無處理入口不能視為完成。人工依原截止證據及固定票券／占用，證據不足繼續待確認，不強制成功或倒補事後票券。
- B 僅結算；下次進場／下一堂 A 的共用票券服務接續失敗，須能辨識「上一堂已結算、後續資格處理異常」。不得為修復接續重扣上一堂，也不因此假造 B 失敗；不另建接續工作表，實際異常回應／呈現沿用相關流程並待技術設計。
- 學生詳細頁的課程出席／結算資訊與既有購票紀錄分開呈現：場次日期、課程／老師、出席結果、固定票券、結算狀態、Consume／Reverse、異常原因及案件進度。
- 先選學生與實際場次，才申請出席／扣堂更正；不直接在某筆購票紀錄上提供任意退堂，避免把購票與課程核銷混為一談。
- 正常 Manual Check-I/O 沿用學生列表入口；館內狀態更正及跨日確認從會員相關操作銜接學生詳細頁，不混入 Schedule。具體版面與 API／DTO 留技術設計。
- 未來 Classes 若提供另一入口，須共用同一後端驗證、交易及稽核服務，不另實作扣退堂邏輯。

### 2. 確認並重新處理

- 暫時性技術錯誤依階段 05 可恢復重試；業務／資料衝突先待人工確認，不能盲目重試。
- Admin 查看原因及預計影響，按「確認並重新處理」；後端重新核對最新資料、歷史資格與並行狀態，不能只接受畫面曾經預覽成功的結果。
- 上一堂修復成功後，系統依原順序恢復該學生後續暫停工作；不重跑已完成者，不讓一人異常阻擋其他學生。
- 若原截止已過，仍使用各堂原截止的歷史資料，不拿目前館內狀態補出席，也不拿事後購買票券倒補資格。
- 尚有衝突繼續保留待確認與原因，不跳過、不強制完成、不重扣；已影響接續票券或反覆更正者仍適用前述不提供一鍵處理的限制。

## 驗收案例

- 無理由不能送出，非授權操作者不能人工操作。
- Admin 正常人工進場仍檢查票券、額度及時間；遲到者不能由此通融上課，不能直接補認出席。
