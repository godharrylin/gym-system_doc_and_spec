# 待確認規格事項

## 1. NEW_ONLY 的 30 天定義

目前程式碼使用 `Now.AddDays(-30)`，屬於 rolling timestamp 判斷。

待確認：

- 是否改成台灣日曆日判斷。
- 若改成台灣日曆日，建議語意為 `assignedDate >= today.AddDays(-30)`。
- `AssignedAt` 的來源時間是否保證為台灣本地時間，或需要先從 UTC 轉台灣時間。

影響：

- 剛好第 30 天的會員是否可買。
- 台灣 00:00 前後與 UTC 跨日時，資格結果是否穩定。

## 2. NEW_ONLY 買過後取消是否仍算買過

目前購買歷史查詢依 `order_items.payment_state != Cancel` 判斷同 SKU 是否買過，沒有明確排除已取消 pass。

待確認：

- 買過 NEW_ONLY 同 SKU 後取消，是否仍不可再買。
- 若取消原因是錯帳或人工取消，是否需要例外。
- 判斷依據要看 order item、pass 狀態，還是兩者都要看。

影響：

- 新客促銷票券是否可被重複嘗試購買。
- 取消訂單與取消 pass 的語意是否一致。

## 3. 註冊可購買清單的規則範圍

目前註冊清單額外排除 `RENEWAL`。

待確認：

- 註冊清單是否只排除 `RENEWAL`。
- 還是應排除所有需要既有會員狀態的規則。
- 若未來新增其他會員資格規則，註冊 API 是否要自動排除。

影響：

- 註冊流程可顯示的方案集合。
- 一般目錄、註冊目錄、購買驗證三者是否一致。

## 4. HIDDEN 的定位

目前 `HIDDEN` 是目錄顯示規則，不進 eligibility service。

待確認：

- `HIDDEN` 是否只代表「不顯示」。
- 若使用者直接指定 hidden 方案購買，後端是否也應明確拒絕。
- hidden 方案是否可能作為內部、客服或特殊流程購買。

影響：

- 購買 API 是否需要額外防線。
- 目錄查詢找不到 hidden 方案是否已足夠。

## 5. 家庭購買暫停範圍

目前購買流程要求受益者剛好 1 人，不套用家庭折扣。

待確認：

- `FAMILY_ELIGIBLE` 是否目前完全不參與購買資格。
- 家庭相關資料是否只保留、不刪除、不套用。
- 未來恢復家庭購買時，是否需要沿用既有 rule code。

影響：

- 現階段是否需要處理 family rule handler。
- 前端是否需要隱藏多受益者入口。

## 6. 續約來源票券選擇規則

舊計畫定義為找最新同家族、已開始、非取消來源票券，且不 fallback 到更舊未用來源。

待確認：

- 目前 repository 實作是否完全符合此語意。
- 若最新同家族票券不可續約，是否一定不再找更舊票券。
- 已取消來源票券是否永遠不可作為續約來源。

影響：

- 續約資格判斷的一致性。
- 多張同家族票券歷史下的購買結果。

## 7. 票券生命週期細節

舊計畫有定義部分生命週期規則，但需和目前 reconcile/pass repository 對齊。

待確認：

- 單堂票是否占用 Active slot。
- FIFO 是否為全域一張 Active，而非依家族一張 Active。
- 逾期關閉 pass 的時機。
- `end_reason` 實際命名，例如 `Expired`、`Expire`、`Cancelled`。

影響：

- 續約有效結束日判斷。
- 排隊票券何時生效。
- 後續測試與資料修復腳本。
