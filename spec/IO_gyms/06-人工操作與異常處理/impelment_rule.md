## 目標與範圍

提供後台操作者人工進／出、館內狀態更正與異常處理，保留完整理由及追溯性。

## 已確認規則

- 人工放行與館內狀態更正分開；更正不需要轉動三叉機。
- 操作選進／出，理由必填，保存操作者與結果。
- 保留異常，包括過期、負堂數與不一致狀態。
- 留館缺票記 Ineligible 與原因，不欠堂、不扣負數、不補結算，不授予回場資格；保存已存在的負數異常不代表允許新的負數扣堂。
- 跨日殘留館內狀態不應自動算進新課程。
- 忘記出場議題保留；沒有實際通行回饋不能推定真實離場時間。
- 階段 05 已確認逐學生結算與失敗隔離；上一堂未完成者暫停其下一堂資格確認，不阻擋其他人，不把處理失敗直接當作無票或 Ineligible。
- 固定占用後票券／堂數變更造成衝突：停止該筆自動結算、記錄原因並轉人工，不換票、不扣負數、不標完成。
- A 歷史不足以可靠還原：保存待人工確認與缺漏原因，不用現在名單推定出席或扣堂。
- 原本 Ineligible 不補結算；原本 Eligible 的結算故障不能直接套用此規則結案，依本文件已確認的人工重新驗證與恢復流程處理。
- 階段 05 保存工作狀態、原因、預定／實際時間及重試紀錄；暫時性錯誤可恢復重試，資料衝突不以按重試強制扣堂，已完成項目不得重扣。

## 第 1 項已確認：人工放行的權限與繞過範圍

確認日期：2026-10-15。本節為目標規則，不代表兩個入口已完成所有實作。

### 1. 操作權限與紀錄

- 第一版人工放行只允許登入後台的 Admin；iPad 裝置授權不能取代 Admin 權限，Staff／Instructor 不因其工作人員進場資格而取得人工放行權限。
- 後端必須驗證操作權限及操作者身分；IP／內網限制是額外防線，不取代 API 授權。本輪未核實實際部署的 IP 隔離。
- 操作選進／出，理由必填，保存實際操作者、方向、時間及結果；操作者是 Admin 不代表被代操作的學生改以 Admin 身分入場。

### 2. Students & Members：正常人工進／出

- 沿用各學生 Actions 中目前停用的 Manual Check-in 入口，後續規劃為 Manual Check-I/O，供 Admin 代該學生操作。
- 人工進場共用正常進場資格驗證：票券、課程時間、額度、回場資格及相關限制都不能繞過；學生遲到不透過此入口通融上課。
- 對已識別使用者的人工出場，維持不因帳號／角色停用、profile 缺漏、票券過期、額度不足或課程時間而阻擋的既有規則。
- 正常人工進／出只有廠商成功回應才記錄成功進出並更新會員館內狀態；事件時間沿用後端收到成功回應時間，不回填較早時間。
- 出席、暫占及扣堂仍依 A／B 和正常生命週期規則，不因人工開門而直接補認出席或立即扣堂。
- 原本正常進場的學生要由後台協助離場，使用此正常人工出場，不使用 Device Test 代替。

### 3. System Settings > Device Test：只開門的取物放行

- 原本在館外、只是臨時進來拿東西者，進／出都使用 Device Test 的對應方向；不另建一個例外放行頁面。
- 這是設備控制／取物用途，不是學生上課授權入口；不建立會員正常進出紀錄、不改會員館內狀態、不建立或補認出席、不占用或扣堂，也不授予同堂回場資格。
- 不把遲到、無有效票券等學生透過取物放行改成可上課；背景工作不得把這類設備操作當作出席證據。
- 原本已有正常館內狀態者不得以取物放行代替正常出場，避免系統仍誤認在館內。
- 取物放行仍須保存操作理由與操作者／結果，並可辨識與純設備測試的不同用途；具體 UI、契約與稽核儲存設計待實作前核對，不將現有設備測試日誌視為業務稽核已完成。

### 4. 操作錯誤與狀態更正的分界

- 已經操作錯誤造成館內狀態不一致，交由獨立的「館內狀態更正」流程處理，不改寫原始進出或設備操作紀錄。
- 更正不發送開門指令，只從後端操作當下生效，不回填過去的實際進出時間，也不自動修改歷史出席／占用／扣堂。
- 回溯出席與扣堂由獨立更正案件處理，不能以館內狀態更正繞過資格、截止及稽核要求；詳見下節。

### 5. 已查閱的入口現況與待對齊差異

- 前端 StudentListPage 目前按鈕為停用的 Manual Check-in，尚未完成正常人工進／出的操作流程。
- Device Test 已有 Admin API 授權及操作者檢查；目前請求只有方向，handler 依 DeviceTestEnabled 設定發送命令，沒有會員出席／進出寫入。
- Device Test 目前已有操作者、方向、結果與追蹤編號的應用程式日誌，但未提供取物理由及用途欄位，不代表已完成上述取物業務稽核。

## 已確認：館內狀態與歷史出席分開更正

以下彙整至 2026-10-16 的決策，不表示已實作。

### 1. 館內狀態更正只當下生效

- Admin 現場確認後，更正目前在館內／館外狀態；理由必填，保存前後狀態、操作者及後端台灣時間，不呼叫三叉機、不覆寫原始事件。
- 不自動改變過去截止名單、釋放過去固定占用或退回已扣堂數；如涉及歷史錯誤，另外建立出席／扣堂更正案件。
- 更正後的狀態可供後續正常截止判斷使用，但仍須通過票券、額度等資格驗證，不能把更正為在館內當成直接授予 Eligible。
- 已確認出席者中途離場，即使未回仍照原規則結算；不能只因目前更正為館外就撤銷該堂出席。

### 2. 獨立出席／扣堂更正

- 2026-10-29 畫面範圍決策：學生詳細頁目前不提供 Admin 取消／撤銷出席、直接選擇 `Cancelled` 或任意改出席狀態；明確同意的日常操作限補登離場與依成功事件確認回場。下列撤銷／補認規則保留作為未來經重新確認後的設計參考，不構成目前 UI 或 API 的實作授權。
- 若未來重新納入，撤銷誤判出席及補認原本符合原截止時刻條件、但被漏記的出席都必須依本節完整查核與交易規則處理。
- 每次以學生＋實際場次為對象，檢查原票券、占用、扣堂及歷史依據；不依現在 Current Plan 重選票，不拿事後付款補原本沒有的資格，不作遲到通融。
- 原本正確的 Ineligible 仍不補結算；歷史不足先待確認，不以現在在館內推定過去出席。
- 撤銷尚未扣堂的誤判出席：保存更正歷史，撤銷有效出席並釋放原占用。若已正式扣堂，須新增對應原 Consume 的 Reverse，不刪原核銷紀錄。
- 沖銷限整筆退回原扣堂，不允許任意輸入加減堂數；月票只更正出席，沒有堂數增減。
- 補認漏記出席需核對歷史資格及額度，經共用占用／結算服務處理，不另寫一套直接扣額度流程；歷史更正不改學生現在的館內狀態。
- 2026-10-25 防重決策：人工 Consume 記 usage_type = Manual，並在同一交易扣堂、寫核銷、連結占用 usage_sn／Consumed 及結算進度；B 取得鎖後查同一 attendance_sn 的 Consume，核對一致則不再扣。usage_type 不代替出席關聯，不新增 ManualDeducted 出席狀態，也不新增核銷 idempotency_key 或扣堂唯一約束。直接 SQL 改餘額不會自動成為已完成本堂核銷；新人工入口須使用共用服務。
- 第一版由 Admin 自己確認並執行，不另設第二位人員審核；後端仍重驗權限、原因與最新資料，不提供略過驗證的強制成功按鈕。

### 3. 第一版不提供一鍵處理的案件

- 已影響後續票券啟用：保存 NeedsReview 原因，先不退堂、不把舊票直接恢復 Active，不自動回滾接續票券或重算其效期。
- 同堂已撤銷／沖銷後又要求再次補認，屬反覆更正：轉待人工確認，不提供一鍵再次扣退；不能藉新 request_id、重建出席或背景重跑繞過。
- 上述案件可以保存及查閱，但更進一步的專案例外解決方式留後續設計；第一版不以直接修改 DB 作為已完成的解法。

### 4. 更正案件、稽核與交易

- 沿用 sdt_att_record 與 sdt_ticket_usage_log，新增 sdt_att_correction 保存申請／進度，及 sdt_att_record_audit_log 保存出席變動前後快照；欄位、CREATE 與實作限制見 [Database.md](../../../Database.md)。只有文件設計，不代表 GymDB 已建表。
- 申請進度可更新，實際出席變動另新增不可覆寫的稽核；保存原因、依據、真實操作者、業務時點與實際處理時間，原 Consume／成功進出紀錄不刪除。
- 出席、占用／額度、Consume／Reverse、出席稽核及案件完成標記須一致提交；同一次請求不得重複執行，同一原 Consume 不得重複沖銷。
- 既有表的結算狀態、撤銷表示法、唯一性與並行控制仍待技術設計；不把兩張新表的 CREATE 當作更正功能已完成。

### 1. 入口與顯示資料

- 第一版正式處理入口放在學生詳細頁；Schedule 保持排課用途，不新增結算操作。獨立 Classes 課程營運總覽頁列後續擴充，不是新增資料表或另一套結算服務。

- B 僅結算；下次進場／下一堂 A 的共用票券服務接續失敗，須能辨識「上一堂已結算、後續資格處理異常」。不得為修復接續重扣上一堂，也不因此假造 B 失敗；不另建接續工作表，實際異常回應／呈現沿用相關流程並待技術設計。
- 學生詳細頁的課程出席／結算資訊與既有購票紀錄分開呈現：場次日期、課程／老師、出席結果、固定票券、結算狀態、Consume／Reverse、異常原因及案件進度。
- 先選學生與實際場次，才申請出席／扣堂更正；不直接在某筆購票紀錄上提供任意退堂，避免把購票與課程核銷混為一談。
- 正常 Manual Check-I/O 沿用學生列表入口；館內狀態更正及跨日確認從會員相關操作銜接學生詳細頁，不混入 Schedule。具體版面與 API／DTO 留技術設計。
- 未來 Classes 若提供另一入口，須共用同一後端驗證、交易及稽核服務，不另實作扣退堂邏輯。

### 2. 課程出席與結算紀錄及進出時間

- 學生詳細頁現有 Attendance History 重新定義為「課程出席與結算紀錄」，使用 `sdt_att_record` 作為每位學生每個實際場次的出席主紀錄；列表欄位依序為出席流水號 `sdt_att_record_sn`、開課日期與時間、課程名稱、出席狀態、使用的票券或方案及 Action。前端已建立示意資料的互動原型；正式 API／DTO、資料串接與保存流程仍待技術設計及實作。
- `sdt_att_record_chk_in_time` 表示該堂出席所採認的簽到時間。A 確認時，除判斷截止時是否在館內，也須取得截止時仍有效的在館區間所對應的最後一次成功進場事件時間並寫入此欄；不得只沿用最早入場請求完成時寫入的時間。若進出歷史不完整或結果不明，轉待確認，不猜測時間。
- 該堂進出追蹤期限為下課後十分鐘，包含截止整點；期限後的進出不再更新該堂出席狀態或簽退時間，仍依當時適用的進出規則處理目前館內狀態。期限內離場、期限後回館時，該堂維持 `CheckOut` 及原離場時間。
- `sdt_att_record_chk_out_time` 表示追蹤期限內該堂出席後最後一次有效的成功離場時間。期限內的一般成功離場須關聯至原 `sdt_att_record_sn` 並更新此欄；若期限內成功回場，前一次離場屬中途離場，清除目前顯示用的離場時間，待期限內再次離場才更新。期限到達時仍在館內者，此欄維持空值，該堂狀態維持 `CheckIn`；此狀態不代表學生現在仍在館內。模擬、失敗、拒絕或結果不明的門禁事件不得當作成功離場時間；進出事件明細仍保留在 `device_record`。
- Admin 現場確認學生剛離館時可直接執行補登離場：若操作時間仍在該堂追蹤期限內，同一交易更新該堂 `CheckOut`／離場時間及目前館內狀態更正；若已超過期限，只更正目前館內狀態，不回寫該堂 `CheckOut`／離場時間。兩種情況均記錄操作者、原因與實際操作時間；不改寫或偽造 `device_record`，不回改過去的出席判定。人工館內狀態更正須作獨立稽核事件，後續較新的真實成功進出事件可更新目前狀態。
- 課程允許回場且仍在追蹤期限內時，成功且關聯至同一出席流水號的實際入場事件使該堂恢復 `CheckIn` 並清除中途離場時間；不覆寫 A 已採認的簽到時間。期限後回館不再改動該堂紀錄。
- 同一學生＋同一實際場次維持一筆 `sdt_att_record`；多次入場、離場與回場各自保留為多筆 `device_record`。課程相關入場／回場請求沿用該出席流水號；一般離場事件的關聯與最終離場更新仍須補入實作。
- 出席狀態沿用 `sdt_att_record_status`。第一版不提供缺席或請假狀態；`CheckIn` 表示出席已確認，`CheckOut` 表示已成功離場，`Pending`、`Cancelled`、`NeedsReview` 依既有語意使用。出席狀態、票券資格及堂數結算是不同資料面向，不得互相代替。
- Action 提供「檢視」及「編輯」。`Pending`／確認中與 `NeedsReview`／待人工處理在此紀錄列表先只檢視。一般編輯只提供已確認的補登離場、依成功回場事件確認回場；不提供 Admin 取消出席或任意選擇 `Cancelled`。這不改變系統可依既有流程自動記錄 `Cancelled` 的規則。編輯須填原因並記錄操作者、異動前後值及業務依據；不得只改狀態或時間。
- 現有程式會在課程入場請求完成時寫入簽到時間，A 會依截止前成功進出事件判斷在館狀態，但尚未把判定所依據的最後進場事件時間回寫；一般課後離場亦尚未關聯該堂出席或寫入 `CheckOut`／離場時間。以上為目標規則，不代表流程已實作。

### 3. `NeedsReview` 原因盤點與處理邊界

以下原因碼依目前 A／B／背景工作的程式整理，供後續定義人工處理與畫面資訊。列出原因不代表已提供 Admin 操作 API；`sdt_att_correction`、稽核表及完整人工恢復流程仍未實作。`NeedsReview` 可能位於出席列、結算工作項目或堂數占用列，不能只讀 `sdt_att_record_status` 判斷整筆結算狀況。

#### 原因碼命名、保存與使用原則

- `processing_state` 描述工作生命週期（例如 `Failed`、`Blocked`、`NeedsReview`）；`reason_code` 描述停止或失敗的具體檢查原因。兩者分開保存與顯示，不以單一 `NeedsReview` 代替原因。
- 每個原因碼對應一個可識別的檢查條件。若不同根因需查不同證據或採取不同恢復方式，應拆分代碼；若處理方式相同，可共用代碼。代碼保持穩定，不含學生、票券等個資或原始例外文字。
- 原因碼目錄需定義：階段（門禁／A／B／背景工作）、觸發條件、需查證據、是否可自動重試、負責角色、證據成立後的安全恢復步驟，以及證據不足時的停留狀態。
- 發生於工作項目的主原因應保存於 `class_processing_item.result_code`，並以 `job_sn`、`item_sn`、`attendance_sn` 對應場次及出席；堂數占用需待確認時，`sdt_ticket_credit_reservation.reason_code` 保存該占用的原因。`sdt_att_record` 目前只有 `remark`，沒有專用 reason_code 欄位；不得把自由文字備註當成穩定機器代碼。若需由出席列直接查碼，欄位或查詢契約仍待技術設計。
- 以 `request_id` 關聯門禁事件；涉及票券占用與扣堂時，也應能追至 `reservation_sn`、`pass_sn`、`usage_sn`。原始例外細節放受限的結構化技術日誌，不放入顯示訊息或 reason_code。
- 目前 `SETTLEMENT_TICKET_CONFLICT` 涵蓋票券缺失、付款狀態／時間不符及票種不支援等條件；`MONTHLY_SETTLEMENT_CONFLICT` 也涵蓋月票有效性及占用／核銷矛盾。實作原因目錄時，若這些條件需要不同排查或恢復流程，應細分代碼；本文件不預先創造尚未落實的代碼。
- 背景工作捕捉到未分類例外時，目前可能只保存 `CLASS_WORK_REVIEW_REQUIRED`。後續需讓分類後的穩定原因碼回到工作項目，並以工作識別碼關聯技術日誌；通用碼只作無法分類時的最後保底，不能掩蓋已知根因。

| --- | --- | --- | --- |

| `CLASS_WORK_TRANSIENT_FAILURE` | 最近暫時性錯誤、重試次數及原場次日期 | 由系統按階段 05 重試；此狀態本身通常是 Failed／可重試，不等同 NeedsReview | 達重試上限或跨日後依上列待處理原因處理 |

#### 狀態位置及角色決策

- A 的 `Review` 可能把既有 Pending／Cancelled 出席列改成 `NeedsReview`；profile 缺失等無出席列的情況可能只有工作項目待處理。B 的 `Review` 可能將有效占用改成 NeedsReview，但出席列仍是 CheckIn／CheckOut。背景工作也可單獨進入 NeedsReview。
- `CLASS_CONFIRMATION_PENDING`、`PREVIOUS_SETTLEMENT_PENDING`、`PREVIOUS_SETTLEMENT_PROCESSING` 是尚未完成／阻擋狀態，不是人工異常原因；暫時性錯誤 `CLASS_WORK_TRANSIENT_FAILURE` 走系統重試，不應直接顯示成需 Admin 更正的異常。
- Attendance History 中 Pending／NeedsReview 只提供檢視；`NeedsReview` 的資料查證與 SQL 修復由開發維運者負責，Admin 不直接改狀態、釋放占用、扣退堂或重啟工作。

### 4. 確認並重新處理

- 暫時性技術錯誤依階段 05 可恢復重試；業務／資料衝突不能盲目重試。上一節列出實際原因及需核對證據。
- 原確認的 Admin「確認並重新處理」入口不納入目前實作。開發維運者修復 SQL 資料時，須依具體原因核對 job／item 狀態、嘗試次數、跨日限制及已提交的出席／占用／核銷；只修正來源資料不會讓 `NeedsReview` 自動重試，也不能把未完成工作直接標為 Completed。
- 上一堂修復成功後，系統依原順序恢復該學生後續暫停工作；不重跑已完成者，不讓一人異常阻擋其他學生。
- 若原截止已過，仍使用各堂原截止的歷史資料，不拿目前館內狀態補出席，也不拿事後購買票券倒補資格。
- 尚有衝突繼續保留待確認與原因，不跳過、不強制完成、不重扣；已影響接續票券或反覆更正者仍適用前述不提供一鍵處理的限制。

## 驗收案例

- 無理由不能送出，非授權操作者不能人工操作。
- Admin 正常人工進場仍檢查票券、額度及時間；遲到者不能由此通融上課，不能直接補認出席。
- 正常人工進／出會呼叫控制器，成功後更新會員館內狀態，失敗不建立成功進出；時間採後端收到成功回應時間。
- 已識別使用者正常人工出場不因過期、額度不足、課程時間或既有帳號／profile 異常而被阻擋。
- iPad 裝置授權及非 Admin 不能呼叫後台人工放行；實際操作者與被操作學生可區分。
- 原本館外者以 Device Test 取物進／出：保留理由及操作結果，不改會員館內狀態，不被 A／B 當成出席或扣堂依據。
