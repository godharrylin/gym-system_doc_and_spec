# 階段 02：開門控制與進出紀錄

日期：2026-10-04。同步日期：2026-10-16。狀態：第二階段程式核心已實作並通過自動測試；實機、正式部署與學生課程授權待後續。

依據：[規格](../gym-io-behavior-spec.md)、[issue](../issue/gym-io-issues.md)。

## 目標與範圍

將已核准的進／出请求轉成廠商 API 指令，分開保存操作結果與館內狀態；客人頁面從 mock 改接真實流程。

## 已確認規則

- 沒有通行回饋，開門成功推定進／出館；不宣稱實際通過。
- 每次嘗試可記錄成功與失敗；收到任意 HTTP 回應不等於成功。
- 失敗不更新成功館內狀態，不直接建立出席或扣堂。
- 工作人員進場身分不列入學生出席。
- 不在前端自行授權、不讓 iPad 直接呼叫廠商控制服務。
- 裝置獨立授權，不持有 Admin 權限；客人電話只識別，不登入或取得會員 token；未授權／已撤銷裝置不能呼叫進出 API。
- 方向由後端站點設定；日常關機再開機不要求每天重新配對。
- 已接受電話冒用的進場風險，不新增客人密碼／驗證碼；後台管理登入另列待辦。

## IO-15 在本階段待討論的具體設計

- 第一點已抽出獨立規劃：[裝置配對、換機、撤銷與授權保存](01-device-pairing-and-authorization-plan.md)；兩張表、配對／換機／自行撤銷、Cookie 與前端配對頁已實作，GymDB 已建表。
- 已確認後端固定配對碼，不先做後台管理配對碼；瀏覽器独立授權、持久 Cookie、新機確認後取代舊機、每個站點只有一份有效授權。
- 配對採五分鐘受保護預覽 token，確認後才換機；裝置可自行撤銷。任意站點的 Admin 管理撤銷入口仍待後續。
- DB 授權不自動到期；Cookie 使用持久保存及續簽。第一版確認內網 HTTP、同源 `/api`、HttpOnly／SameSite=Strict、來源檢查與配對限流；正式金鑰保存路徑待 NAS 部署設定。
- 站點／裝置資料、API 授權策略、方向映射及管理紀錄均已落實於程式；實際控制器方向仍待現場核對。

## 前置依賴與預計項目

1. 階段 01 識別及資格結果；學生完整資格另依階段 03／04。
2. 核對現有資料結構，設計操作紀錄、成功進出事件及館內狀態關係。
3. 建立廠商控制介面，控制器序號、位址與方向映射使用設定，不沿用測試硬編碼。
4. 定義成功解析、錯誤、通訊失敗與結果不明的回傳及紀錄。
5. 定義事件業務時間、操作身分及進出順序，讓 A 能還原截止狀態。
6. Check-In／Check-Out 前端接真實結果，保留可理解的拒絕原因。
7. 設計外部 API 與資料庫無法原子提交時的紀錄／修復方式，不在網路等待期間無限持有資料庫交易。

- IO-09／IO-12：schema 與程式結果分類已完成；廠商實機成功內容及實際方向映射待設備驗收。
- IO-14：逾時已開門的最低處理策略；完整重試與多裝置優化後排。

## 驗收案例

- 未通過資格不呼叫控制器。
- HTTP 成功但廠商結果失敗，不更新館內狀態。
- 成功進／出保存方向、身分、時間及結果；出場異常可追溯。
- 逾時／結果不明不直接顯示確定成功，也不無條件再送一次。
- 開門成功但資料保存失敗的情境可發現、可人工處理。
- 兩個頁面方向固定，不因客人改任意參數轉成管理員操作。

## 本階段不包含

實際通行感測器、正式 NAS 部署、課程扣堂及完整高併發硬體命令防重。

- `POST pairing-preview`、`POST pair`、`GET session`、`POST revoke` 已完成；配對與 Admin JWT 分離。
- `POST passage` 已完成裝置重驗、電話／角色／基本票券驗證、request ID 防重、控制器結果分類及 `device_record` 保存。

- 工作人員進場及已識別使用者出場可進入控制流程；學生進場在階段 03／04 完成課程時段與額度占用前固定拒絕，不會誤把基本票券資格當成完整開門授權。

- 前端 `/#/checkin` 已接裝置配對及電話送出，不沿用 Admin token client，也不自動重試不確定的開門操作。
- 尚待：實體三叉機成功／失敗／逾時驗收、控制器 SN 與 DoorNO 現場核對、正式內網網址／Cookie 金鑰路徑、階段 03／04 學生完整授權，以及成功後 DB 最終更新失敗的人工處理入口。
