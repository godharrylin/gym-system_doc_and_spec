# 票券購買 UI/API 規格

## API 角色

前端可以顯示方案與送出購買，但購買資格的最終權威在後端。

目前相關 API 語意：

- 一般方案目錄：回傳目前可上架顯示的方案資料。
- 既有會員個人化可購買清單：依學生資格過濾可購買方案。
- 註冊可購買清單：排除 `RENEWAL`，用於新會員註冊流程。
- 購買 API：重新檢查學生、方案、數量、價格、付款、eligibility。
- 未付款訂單付款 API：付款當下重新檢查方案、價格與資格。

## DTO 欄位語意

建議對外 DTO 保持以下語意：

- `id`：方案 id / SKU。
- `name`：方案名稱。
- `familyCode`：方案家族。
- `price`：數字，不使用格式化字串。
- `days`：效期天數，可為 null。
- `sessions`：堂數，可為 null。
- `type`：票券類型。
- `eligibilityRuleCodes`：後端用於資格判斷的規則代碼。
- `purchaseKind`：可由 `eligibilityRuleCodes` 推導，不建議新增 DB 欄位。

## 前端顯示規則

前端不應自行判斷續約資格，也不應保留 demo student id。

建議：

- 既有會員畫面呼叫個人化可購買清單。
- 註冊畫面呼叫註冊可購買清單。
- 方案購買送出後，依後端結果更新列表。
- 當購買、取消、付款、資格重算後，重新載入方案清單。
- 若原本選取的方案已不在清單，清除選取狀態。
- `canCancel` 等狀態應由後端輸出，不由前端自行推導。
- 日期顯示使用台灣日期語意，不用 `toISOString()` 直接切日期。

## 家庭功能暫停

目前家庭購買暫停：

- 受益者必須剛好 1 人。
- 不套用家庭 95 折。
- 不刪除既有 `FAMILY_ELIGIBLE` 設定，保留未來恢復空間。

未來若恢復家庭功能，需要補：

- 多受益者 eligibility all-or-nothing 規則。
- 家庭成員關係檢查。
- 價格折扣與四捨五入規格。
- 前端多受益者選擇與錯誤顯示。
- 交易中任一受益者失敗時的整體 rollback。

## 錯誤處理建議

前端應以後端錯誤碼顯示原因，尤其是：

- 學生不存在或非有效學生。
- 方案不存在、未啟用或不可購買。
- NEW_ONLY 不符合。
- RENEWAL 不符合。
- 已有排隊票券。
- 續約來源已被占用。
- 未付款訂單價格變動。
- 家庭購買目前不可用。
- 數量不合法。

## 建議測試

- 註冊清單不顯示 RENEWAL。
- 既有會員符合續約資格時顯示續約方案。
- 符合續約資格時，標準方案仍可買。
- 前端送出不可購買方案時，後端拒絕。
- 未付款訂單建立後方案改價，付款時拒絕。
- 購買成功後重新載入清單並清除失效選取。
- 台灣跨日情境下日期顯示不偏移。
