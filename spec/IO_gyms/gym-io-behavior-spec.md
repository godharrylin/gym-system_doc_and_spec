## 1. 範圍與前提

- 第一版目標：客人透過兩台 iPad 的瀏覽器輸入電話進／出館；系統操作者可以人工控制進／出。
- 一台 iPad 負責進場，另一台負責出場。
- 票券不綁特定課程，但堂票的扣堂依課程出席結算，不依每次開門扣堂。
- 只有一間教室，同一時間只有一堂課。目前不考慮陪同或在館內等下一堂的其他用途。
- 本次討論先假設廠商 API 穩定運行；實際部署、NAS 相容性及硬體驗證不因本文件而視為完成。
- 沒有實際通行回饋，因此接受「控制器開門成功就視為已進／出館」。這是系統推定，不是實際通行證明。

## 2. 電話識別與角色

### 2.1 電話識別

- 以輸入電話識別使用者。查不到電話時，不呼叫開門 API。
- 客人進出只接受台灣手機 `09xxxxxxxx`；註冊／編輯的其他數字及後端格式驗證暫不調整，不批次改既有電話。
- 出場也必須輸入可識別的電話；電話不存在或未輸入，不放行。
- 後台 Students & Members 的模糊搜尋不是客人進出授權流程；進出識別需要完整電話的精確對應。
- 電話只能識別帳號，不等同證明是本人；使用者已接受電話冒用的進場風險，包括工作人員電話，不增加客人密碼或驗證碼。

### 2.2 角色優先

- 進場要求 `users.usr_active = 1`，只採用 `user_role.user_role_is_active = 1` 的角色。
- 使用者包含啟用的 Admin、Staff 或 Instructor 任一角色時，以工作人員身分進場，呼叫開門 API 放行。
- 同時有工作人員及 Student 角色時，仍以工作人員身分為主；這次進場不列入學生課程出席與扣堂。
- 只有 Student 資格的進場，需檢查票券、課程進場限制及可用額度。
- 工作角色停用但 Student 啟用時，走學生票券驗證；沒有適用角色則拒絕進場，顯示「尚未註冊會員」。
- Student 缺少 `sdt_profile` 時拒絕進場，顯示「會員資料異常，請洽工作人員」並記錄，不誤報過期。
- 工作人員內部角色紀錄呈現及在館角色變更留後續銜接，不推定已確認新排序。

## 3. 票券生命週期與效期

- 共用既有票券生命週期及非單堂票優先規則；不得另外複製一套進場專用的啟用排序。
- 抽出共用應用服務，供票券流程及进場流程整理當前票券，並同步 `sdt_profile` 當前票券快照。
- 不把會員列表的 Current Plan 顯示查詢當作進場授權。列表查詢是唯讀投影，不會啟用下一張票。
- Student 的可用票券已過期時，不呼叫開門 API，顯示票券過期原因。
- 無票、未啟用、取消、耗盡等狀況須區分；詳細拒絕原因、占用不足及下一張票選擇整合於階段 01／04 討論。
- 月票及有期限的堂票效期依台灣日期判斷。到期日整天有效，次日才因日期到期失效；單堂票既有無到期日規則不變。
- 資格與事件時間共用後端 `IClock` 的台灣時間，不採 iPad 時間判斷；付款、取消、進出與扣堂等事件保留精確時間，不能將到期日零點當作當天已過期。
- 堂票剩餘額度與待結算占用額度應區分，不能僅靠帳面剩餘堂數認定可再參加下一堂。
- `sdt_profile` 快照保留用途，但不單独作為授權或占用額度的最終依據。
- 來源因 Depleted 耗盡時，符合條件的續約票可耗盡當天接續；來源因 Expire 到期則維持到期日隔天，較晚付款仍不得早於付款日。
- 正常啟用沿用共用生命週期的付款及 Depleted／Expire 日期公式，續約可購買期限及取消重訂期限不變。2026-10-23 第一版縮小範圍：跨日未完成的 A／B 轉人工，不自動補扣或重算歷史接續效期，不把事後購買／付款的票回填過去；完整歷史還原列後續擴充。

## 4. 課程進場限制與最終出席

### 4.1 工作命名

- A：課程開始十分鐘後，確認最終出席學生並建立／固定堂票額度占用。
- B：課程結束十分鐘後，依已成立的出席及占用正式扣堂、結算。
- 討論中曾將「第二堂開始十分鐘後查出席」稱為 B，依工作內容統一稱 A。

### 4.2 十分鐘緩衝與截止名單

- 開課後前十分鐘是學生決定是否留下參加該堂的緩衝時間。
- A 認定「截止時間仍在館內」的 Student 為出席，不使用「前十分鐘曾經在館內」的規則。
- 緩衝期的出席狀態為 `Pending`；確認出席後中途離場不改回 Pending，依進出紀錄判斷離場及返回。
- 例如第二堂 19:00 開始，學生 19:05 離場且截止時間未回來，不認定第二堂出席。
- 學生離場後於截止前重新進場，若截止時在館內，仍可成立第二堂出席。
- 截止後未取得該堂出席資格的 Student 不得再進場；月票與堂票都適用。
- 已取得該堂出席資格者可中途離場並回場，同一堂不得因多次進出重複扣堂。
- 同堂回場限 Eligible 有效出席，保留到該堂結束後十分鐘；Ineligible／取消預參加不授予回場資格。
- 截止包含開課後第十分鐘整點，19:00 開課為 `<= 19:10:00`；採後端收到廠商成功回應的時間，不採請求送出或 iPad 時間。
- 截止整點成功進場可納入，整點成功出場且未回者不納入；截止前送出、截止後成功不追認。封存及同時事件排序待技術設計，不能讓排程競態決定出席。

### 4.2.1 課間預入及無課程時段

- 不普遍開放提早到場；只在上一堂結束後十分鐘內開放課間預入。先判上一堂有效回場，沒有才驗下一堂資格並建立 Pending／暫占。
- 下一堂開課時不直接確認出席，統一到開課後十分鐘截止確認；離場至截止未回則取消預參加、釋放暫占，不取消票券。
- 課間窗口結束後、下一堂尚未開始的空檔拒絕新進場；下一堂開始後依其正常十分鐘進場窗口。
- 當天沒有課、最後一堂結束後拒絕新學生；最後一堂的有效出席者仍可在同堂回場期限內返回。
- 已識別使用者出場不限上述時段；工作人員沿用角色放行。詳細例子及技術待辦見 [階段 04](04-出席確認與額度占用/impelment_rule.md)。

### 4.3 續上下一堂

- 每堂獨立套用相同截止名單規則。
- 留在館內並在下一堂截止時間仍在館內者，可由系統辨識下一堂出席。
- 曾有 check-out 不代表不能參加下一堂；需綜合截止前的進／出紀錄判斷最終館內狀態。
- 每堂需各自處理額度；來源可區分一般進場與系統自動辨識續堂，具體代碼待討論。
- 已固定出席後中途離場、直到下課也沒回來，仍算上過該堂，B 仍需結算。
- 相鄰課程先結算上一堂，再透過共用生命週期服務接續符合條件的票券，最後確認下一堂出席；留館不需要重新輸入電話或新開門事件。2026-10-23 已確認 B 只結算；接續由下一次進場／下一堂 A 在前置 B 完成後觸發，不包含在 B 交易內，不另建接續排程或工作表。

## 5. 額度占用與扣堂

- 進場先檢查並暫占額度；截止前離場未回則釋放，截止時在館內由 A 確認出席並轉固定占用；固定後離場不釋放，B 正式扣堂。
- 月票記錄出席，但不扣堂票額度。
- 堂票每位學生、每個實際課程場次最多一筆有效出席／占用，每筆出席最多正式扣堂一次。
- 同堂進出不新增一次扣堂；下一堂是新的出席與額度需求。
- 扣堂與結算完成標記須在同一筆資料庫交易內完成。
- 首次進場時應檢查額度，不能等 A 才第一次發現不足。
- 以出席截止時整理後的票券固定該堂 pass 關聯，B 不依當下 Current Plan 重新選票；暫占移轉、交易及補跑還原待技術設計。
- 使用 `sdt_att_record_ticket_eligibility_state` 區分 Eligible／Ineligible，資格與出席事實分開；堂票 Eligible 要有有效占用，月票不占用堂數。
- 无可接續票券／可用額度仍留館：保存事實，標記 Ineligible 及 remark，不強填已耗盡舊票；不欠堂、不扣成負數、不補結算、不授予同堂回場資格。後來買票不自動補結算本堂。
- 不解析 remark 決定扣堂；每堂防重複及占用資料仍需設計。異常提示功能可後排，不可因此略過資格處理。
- 課程扣堂造成耗盡的 `ended_at` 使用課程結束時間，不用 B 實際執行時間；一般 Expire／Cancelled 規則不變。
- 固定占用後，票券取消或堂數人工調整若造成結算依據衝突，停止該筆自動結算並保存原因，轉人工處理；不自動換票、不扣負數、不直接宣告完成。
- 原本 Eligible 的系統／資料結算故障不等於 Ineligible，不能以「不補結算」規則消除未完成工作；Admin 確認並重新處理後，重驗成功才依原順序恢復未完成工作。

## 6. 開門、館內狀態與出場

- 開門操作紀錄、館內狀態、課程出席分開保存／處理。
- 每次開門嘗試皆可記錄，包括失敗；只收到 HTTP 回應或錯誤內容不能認定開門成功。
- 會員正常進／出只有符合廠商成功結果的操作才更新館內狀態；目前以該成功結果推定進／出館。Device Test 設備測試／取物只控門，不更新會員館內狀態，見第 7 節。
- 失敗不建立成功進／出，也不因該次失敗建立出席或扣堂。
- 已識別使用者的出場，不因帳號／角色停用、profile 缺漏、票券過期、額度不足或異常負堂數而拒絕。
- 過期及其他出場異常需要標註；標註位置與欄位於資料設計時確認。
- 無法識別的出場及服務故障仍需實體／人工處理途徑，不能將本系統視為唯一逃生機制。

### 6.1 裝置授權與電話識別

- iPad 使用獨立裝置授權，不持有 Admin 權限；未授權／已撤銷裝置不能呼叫進出 API。
- 進／出方向由後端站點設定決定，不相信客人任意修改方向參數。
- 客人電話只識別要進出的人，不登入帳號、不取得該人的 access／refresh token。
- 初次啟用後日常關機再開機不要求每天配對；配對、換機、撤銷、到期／續期、保存及 API 設計留階段 02。
- 後台只憑電話登入的管理風險獨立待辦，不影響客人電話進出的需求，也不因電話進場風險接受而視為後台風險已接受。

## 7. 人工操作

- 提供人工進／出放行，操作時選方向，理由必填，保存操作者及結果。
- 第一版人工放行僅限登入後台的 Admin，後端須驗證；IP／內網限制不取代 API 授權，iPad 裝置不取得此權限。
- Students & Members 各學生的停用入口規劃為正常 Manual Check-I/O：人工進場沿用正常票券、額度、時間及回場驗證，不通融遲到；已識別使用者人工出場不因過期、額度不足或課程時間而拒絕。
- 正常人工進／出於廠商成功回應後記錄會員進出、更新館內狀態；事件時間及出席／扣堂沿用正常規則，不能因操作者是 Admin 而把學生當工作人員或直接補認出席。
- 原本館外者臨時取物，進／出都使用 System Settings > Device Test，只控門、不改會員館內狀態、不參與出席／占用／扣堂、不授予回場資格，不以此讓遲到學生上課；仍須理由及操作追溯。
- 原本正常進場者要離場，使用正常人工出場；誤操作造成狀態不一致，另走館內狀態更正，不覆蓋原始紀錄。
- 另外新增「更正客人館內狀態」，與發送開門指令的人工放行分開。
- 更正保留前後狀態、原因及操作者，不需要讓三叉機轉動。
- 館內狀態更正只操作當下生效，不回填過去進出，不自動回溯出席／占用／扣堂；原出席者中途離場仍依原規則扣堂。
- 出席／扣堂更正以學生＋實際場次另建案件，允許撤銷誤判及補認符合原截止歷史資格的漏記；不通融遲到、不倒補事後付款，不拿現在 Current Plan 或館內狀態代替歷史。
- 第一版 Admin 自行確認並執行，不另做第二人審核；理由、依據、前後結果、操作者與時間須保存。沿用出席／核銷表，新增更正申請及出席稽核表，Database.md 僅有文件設計，未建表。
- 已扣堂的更正限整筆 Reverse 對應原 Consume，原扣堂不刪，不提供任意額度加減；月票更正無堂數增減。出席、占用／額度、核銷、稽核與完成標記須一致提交，不重複扣退。
- 已影響後續票券啟用或反覆撤銷／補認的案件先待人工確認，不一鍵再次扣退、不直接恢復舊票 Active，進一步專案解決方式列後續。
- 第一版正式查閱／更正／重新處理入口放學生詳細頁，課程出席結算與購票紀錄分開；Schedule 僅排課、不加結算操作，獨立 Classes 頁列後續擴充。
- 詳細決策、取物稽核與入口待對齊項目見 [階段 06](06-人工操作與異常處理/impelment_rule.md)。本節不表示正常人工入口或 Device Test 取物流程已實作完成。

### 7.1 忘記出場與跨日殘留

- 以台灣日曆日午夜 00:00 換日；昨日未結束館內狀態保留為跨日待確認，不生成假的午夜出場，不直接當成今日出席，也不等於 Ineligible。
- 今日須重新正常驗證並成功進場，或 Admin 現場確認後由館內狀態更正當下生效；昨日殘留不得單獨阻擋今日合法進場，已識別使用者出場仍允許。
- 今日截止仍未重新確認，不憑昨日狀態認出席；歷史補認另走更正案件。Device Test 取物不建立今日館內／出席狀態。
- 各進出、出席及查詢流程共用日期檢查，不完全依賴午夜排程；主動清單／通知可以後續擴充，但服務隔日重啟仍不得錯用昨日狀態。
- 昨日已成立出席不因換日清除；第一版昨日未完成的 A／B 今日一律轉人工確認，不自動補扣，保留原截止歷史及固定票券／占用供重驗。當日狀態、事件與稽核的 schema 仍待設計。

## 8. 背景工作與補跑

- 每堂使用穩定的實際場次 ID，保存開始／結束時間。
- A、B 保存工作狀態；重啟後查找已到期但未完成的工作。
- 2026-10-23 第一版界線：同日未完成工作按既有防重／重驗流程處理，跨過原場次台灣日曆日仍未完成的 A／B 一律 NeedsReview，包括 A 已固定而只有 B 延遲者；不能將 NeedsReview 當成 Completed 或 Ineligible。
- A 晚跑時依進出歷史還原截止時間館內狀態，不使用補跑當下名單。
- 若某學生歷史不足以可靠還原，保留待人工確認與缺漏原因，不猜測出席或扣堂；其他可還原的學生照常處理。
- 同一堂 A、B 都逾時時，先完成 A，再執行 B。
- 保存預定執行時間與實際執行時間，防重跑／防重複扣堂不依賴記憶體旗標。
- 可以共用一個背景處理程式，每個階段有自己的到期時間與狀態；相鄰課程的業務順序已確認為上一堂 B → 接續票券 → 下一堂 A，鎖定及恢復機制待設計。
- B 同一交易保存扣堂、核銷、占用 Consumed、必要耗盡標記與結算完成，不負責下一張票啟用。後續共用服務接續失敗，不回滾或重扣已完成 B；無下一張票是正常資格結果，不是上一堂結算失敗。
- 2026-10-25 確認：B 採後端台灣時間嚴格 `now > 下課時間 + 10 分鐘`，不是 `>=`；後端自動觸發，不靠學生輸入電話或前端查詢才執行。月票只完成工作進度，不新增零堂數核銷。
- 核銷以 attendance_sn ＋ Consume 作業務防重，usage_type 只記 Manual／Auto_Settlement；人工與 B 共用服務，在同一交易依既定順序鎖定後查核。不新增核銷 idempotency_key 或同堂扣堂唯一約束，既有主鍵／占用與工作防線保留；接受直接 SQL／未遵守流程者仍可繞過的限制。
- B 暫時性技術錯誤最多自動嘗試 3 次（含第一次），相鄰嘗試至少隔 15 秒；資料衝突／不明核銷直接人工，第三次仍失敗或已跨日亦轉人工，不因重啟重置次數或重扣已完成者。
- 進場收到「B 處理中」的簡單版回覆：不開門，前端停止轉圈、清空電話、恢復可操作，提示「上一堂結算處理中，請稍後重新輸入電話並確認進場」。不新增定期輪詢 API、不自動重新驗證或重送開門；再次操作仍受原截止限制，不因等待延長資格。其他失敗情境的電話清除規則另行對齊。
- 接受的代價：下一張票不保證結算當下立即啟用，錯誤可能在下次資格檢查才暴露；跨日未完成 A／B 都增加人工處理成本。學生詳細頁的查閱、確認與恢復入口仍為第一版上線必要工作，不因暫緩三張完整歷史表而省略。
- 補跑保留原業務時間及實際處理時間，不拿補跑時才買的票或現在館內狀態覆寫截止結果。
- 各學生獨立結算；單人失敗不阻擋其他人，保留未完成原因，重跑只處理未完成者。該學生上一堂未完成時暫停其下一堂資格確認，不將處理失敗誤標無票／Ineligible。
- 保存失敗原因及重試紀錄；暫時性錯誤採可恢復重試，資料／資格衝突轉人工，不以重試強扣。人工查閱／更正／重新處理入口已確認為學生詳細頁，不在 Schedule 加結算操作。
- Admin 查看原因與預計影響，按確認並重新處理後由後端重驗；上一堂修復成功，才依原順序恢復該學生後續未完成工作。截止已過仍查原歷史，尚有衝突保持待確認，不跳過、不重扣。
- 本版不處理跨夜課／下課結算跨午夜的正常排程邊界；跨營業日館內殘留與補跑恢復仍分別屬 IO-08／IO-05。
- A、B 各依開課／下課後十分鐘到期，不採統一下課後才首次執行 A；共用背景程式不改兩階段業務時間。

### 8.1 實際課表的第一版規則（2026-10-10 確認）

- 保留查詢未生成週時即時建立場次；整週完全沒有任何場次才由啟用模板生成。

- 課表頁面與背景流程共用穩定的實際場次 ID、時間與老師，不以 mock 或課名重建出席關聯。
